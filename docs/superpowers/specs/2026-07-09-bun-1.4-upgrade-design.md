# Bun 1.4 Upgrade + Benchmark Instrumentation — Design

**Date:** 2026-07-09
**Status:** Approved (design), pending spec review
**Branch:** `bench/bun-baseline`

## Goal

Benchmark the Bun **Rust rewrite** (shipped only as canary `1.4.0-canary.1`,
commit `fc865b398`) against the current Bun **1.3.11** landscape run, and
honestly refresh the benchmark figure shown on the site (currently claimed as
"53 seconds"). Establish a **real 1.3.11 baseline first**, then re-measure on
the Rust build, so any speed claim is measured — never fabricated.

## Reality Check (updated after verification)

**There is no stable Bun 1.4.** Latest stable is `1.3.14`; npm's `canary` tag is
still the old Zig line (`1.3.13-canary`). The Rust rewrite exists only as a
special preview build (`1.4.0-canary.1`, commit `fc865b398`) installed via
`bun upgrade --canary`. `setup-bun@v2` accepts a **commit SHA** as
`bun-version`, so we pin `fc865b398` to get that exact Rust build reproducibly
in CI — a fixed commit, not a moving tag.

## Locked Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Benchmark Bun build | Pin **Rust canary commit `fc865b398`** in the benchmark workflow | Only way to run the Rust build; a fixed SHA is reproducible |
| Scope of the canary pin | **`deploy-datasets.yml` only** | `ci.yml`/`deploy.yml` stay on stable `1.3.11`; preview isolated to the benchmark |
| `packageManager` / site `engines.bun` | **Unchanged** | Cannot point at a canary commit; no stable 1.4 exists |
| Benchmark measurement | **Add timing instrumentation** to the job | Every run self-reports duration |
| Benchmark org | **effect-TS** | Matches the site's "17 repositories" copy |
| effect-TS as published dataset | **Yes, promote to `main`** | Site markets Effect-TS; make reality match the copy |
| Baseline capture | **Dispatch CI on a branch** | Hardware-comparable to "standard GitHub Actions runner" |
| Pre-existing dep bump | **Committed as its own commit first** | Keeps deps constant across both runs; Bun build is the only variable |
| `benchmark_only` guard | **Add it** | Lets a benchmark run skip Azure publish (no side effects) |

## Architecture / Components

The change touches three independent surfaces, each verifiable on its own:

1. **CI workflow instrumentation** (`deploy-datasets.yml`)
   - A `benchmark_only` boolean `workflow_dispatch` input (default `false`).
   - A timer around the `analyzeLandscape` step that computes elapsed seconds
     once, writes `landscape_seconds` to `$GITHUB_OUTPUT`, and appends a
     human-readable line to `$GITHUB_STEP_SUMMARY`.
   - When `benchmark_only == true`, the Azure login / upload / verify / summary
     steps are skipped (guarded by `if:`), so a benchmark run has no publish
     side effects. Scheduled and push-triggered runs are unaffected.

2. **Landscape config** (`landscape-config.json`)
   - `githubOrgs` → `["effect-TS"]`, promoted to `main` as the published dataset.

3. **Benchmark Bun pin (one line)**
   - `bun-version: 1.3.11` → `bun-version: fc865b398` in `deploy-datasets.yml` only.
   - `ci.yml`, `deploy.yml`, `packageManager`, and `engines.bun` stay unchanged
     (no stable 1.4 to point them at; canary is isolated to the benchmark).
   - `bun.lock` is already regenerated (committed in the dep-bump commit) and is
     `lockfileVersion: 1`, which the 1.3.11 baseline runner also reads.

4. **Site figures** (`technology.astro`, `TechnologyView.astro`)
   - Updated with the measured Rust-build duration in both files.

## Timing Step (reference implementation)

```yaml
- name: Generate hosted landscape dataset
  id: analyze
  run: |
    start=$(date +%s)
    bun run apps/cli/src/index.ts analyzeLandscape \
      --config _landscape-config.hosted.json \
      --outputFolder datasets/${{ steps.landscape.outputs.dataset_name }} \
      --concurrency 4
    elapsed=$(( $(date +%s) - start ))
    echo "landscape_seconds=$elapsed" >> "$GITHUB_OUTPUT"
    echo "### Landscape analysis: ${elapsed}s (Bun $(bun --version))" >> "$GITHUB_STEP_SUMMARY"
```

`workflow_dispatch` input:

```yaml
on:
  workflow_dispatch:
    inputs:
      benchmark_only:
        description: "Skip Azure publish; only measure landscape duration"
        type: boolean
        default: false
```

Azure steps get: `if: ${{ steps.storage.outputs.storage_ready == 'true' && inputs.benchmark_only != true }}`
(and the Azure login / storage-resolve steps gain `if: ${{ inputs.benchmark_only != true }}`).

## Rollout Phases

### Phase 0 — Real baseline on Bun 1.3.11
1. On `bench/bun-baseline`: add the timing step + `benchmark_only` input.
2. Point `landscape-config.json` at effect-TS.
3. `gh workflow run deploy-datasets.yml --ref bench/bun-baseline -f benchmark_only=true`.
4. Read `landscape_seconds` from the run summary → the true 1.3.11 baseline for
   effect-TS. Record it; correct the site's "53 seconds" if it differs.

### Phase 1 — Pin the Rust build in the benchmark workflow
1. Change `bun-version: 1.3.11` → `bun-version: fc865b398` in `deploy-datasets.yml`.
2. Locally (already on the Rust canary) verify the codebase runs on it:
   `bun install --frozen-lockfile`, `bun test`, `bun run typecheck`, `bun run build`.

### Phase 2 — Re-measure on the Rust build + refresh site
1. Dispatch the benchmark again on the branch (`benchmark_only=true`), now on `fc865b398`.
2. Update both `technology.astro:149` and `TechnologyView.astro:145` with the
   measured Rust-build duration.
3. Report the true number regardless of direction.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| 1.3.11 baseline rejects the canary-written lockfile | `lockfileVersion: 1` unchanged; if frozen install fails on 1.3.11, run the baseline with a non-frozen `bun install` (same package.json → same resolved versions) |
| `setup-bun` cannot resolve commit `fc865b398` | Fall back to `bun-download-url` with the exact Rust asset URL, or run `bun upgrade --canary` in a step |
| Benchmark run publishes effect-TS to Azure unintentionally | `benchmark_only=true` skips all Azure steps |
| Local (Apple Silicon) number not comparable to runner claim | Capture baseline and Rust numbers both via CI dispatch |
| effect-TS promotion changes what the site publishes | Intentional and approved — site copy already describes effect-TS |

## Measured Results

Methodology: analyze-step wall time from the GitHub Actions jobs API
(`started_at`→`completed_at` of "Generate hosted landscape dataset"), which
brackets the `analyzeLandscape` command (clone + scan + aggregate). Same method
for both runs; deps and config identical, so the Bun build is the only variable.

- **Bun 1.3.11 baseline** (effect-TS, 18 repos, 1,271,873 LOC, concurrency 4):
  **51s** — run [29029058080](https://github.com/opsydyn/planetnik/actions/runs/29029058080).
- **Bun 1.4.0-canary.1 Rust build** (`+fc865b398`, same workload):
  **49s** — run [29030665288](https://github.com/opsydyn/planetnik/actions/runs/29030665288).
  The `bun-download-url` canary asset resolved to exactly `fc865b398`, the
  intended commit.
- **Delta: ~2s / ~4% — within single-run noise.** This workload is dominated by
  git-cloning 18 repos over the network, not CPU, so the Rust runtime's
  speedups barely surface. A single sample each cannot reliably distinguish
  49s from 51s.
- Note: effect-TS resolves to **18 repositories** (site copy says "17" — correct
  to 18 in Task 6). Existing "53 seconds" claim is roughly accurate.
- Setup note: `setup-bun@v2` rejects commit SHAs (semver-only); the workflow
  fetches the Rust build via `bun-download-url` (rolling canary asset).
